# AI YouTube Autonomous System — V1 Architecture Blueprint

**Status:** Proposed architecture  
**Version:** 1.0  
**Repository:** ErfanJavadian/Ai_Agent_Youtube  
**Default branch:** main  
**Date:** 2026-11-17

> This blueprint defines a realistic first release. It separates deterministic automation from creative and judgment-heavy tasks that still require human review.

## 1. Product definition

AI YouTube Autonomous System (AI-YAS) is a GitHub-managed, phone-accessible workflow for producing English-language, faceless documentary videos about AI, science, technology, and the future of humanity.

The user supplies a topic. The system creates a structured project, coordinates repeatable production steps, generates programmatic motion-graphic assets, renders a video where a verified execution environment is available, performs mechanical quality checks, and exports a publishing package.

**V1 is an assisted production system, not fully autonomous creative intelligence.** It automates deterministic work and makes judgment-heavy work explicit and reviewable.

### V1 target outcome

For one approved topic, V1 should:
1. Create a project workspace from a validated topic brief.
2. Store research notes, source URLs, claims, and citations.
3. Import and validate a script and storyboard.
4. Generate simple visual assets using SVG, HTML/CSS, and Python imaging tools.
5. Assemble narration supplied by the user or generated by a locally available, tested tool.
6. Render a video through FFmpeg where the runtime supports it.
7. Run structural and media-quality checks.
8. Export a review package: video, script, sources, thumbnail, description, chapters, and publishing checklist.

V1 does not promise one-click autonomous publishing or fully AI-generated cinematic footage.

## 2. Non-negotiable constraints

- No paid or external AI APIs in V1. AI API keys must not be a runtime dependency.
- Internet may be used for research and manual YouTube Studio access, subject to source terms and platform rules.
- GitHub is the primary development and project-management environment.
- The owner primarily works from an Android phone with limited memory and no budget.
- Heavy rendering and large local models must not be assumed to run on the phone.
- Prefer free, portable, inspectable tools and small dependencies.
- Never publish without explicit human approval.
- Do not bypass CAPTCHAs, account protections, rate limits, copyright restrictions, or platform safeguards.

## 3. Feasibility boundary: intelligence without AI APIs

A workflow engine can automate file handling, validation, rendering, and repeatable transformations. It cannot independently provide frontier-level research synthesis, compelling long-form writing, or creative direction simply by being called an agent.

V1 therefore uses a **Human-in-the-loop Intelligence Bridge**:
1. The system prepares a scoped task packet and prompt for a judgment-heavy stage.
2. The user may manually open that packet in an AI chat interface.
3. The user imports the resulting answer into the project workspace.
4. The system validates the artifact structure and records its provenance.
5. A human approves consequential claims and creative decisions.

This bridge does not call an AI API or automate a third-party AI website. Rule-based helpers may support word counts, timing estimates, source metadata, and consistency checks. Heuristic scores must never be presented as proof of factual accuracy.

## 4. System context

The logical workflow is:

**User / Browser → Project Interface → Workflow Orchestrator → Stage Engines → Quality Control → Publishing Package → Human Approval → Manual YouTube Studio Upload**

The orchestrator reads and writes project state. The stage engines are independently testable. The human approval gate is mandatory before public release.

GitHub stores source code, documentation, issues, and version history. It is not assumed to be a continuously running application server. GitHub Actions may run bounded tests or jobs, but video rendering must be tested against actual runner limits before becoming a required workflow.

## 5. Architectural components

### 5.1 Project Interface
**Responsibility:** Create and inspect production projects.

V1 prioritizes a simple command-line workflow and portable project files. A lightweight browser interface can follow after the core pipeline is proven.

Inputs: topic, working title, target duration, audience, narrative objective, language (English by default), optional source URLs, and user-provided materials.

Outputs: project ID, manifest, current stage, validation status, and next required action.

### 5.2 Workflow Orchestrator
**Responsibility:** Execute stages in order, preserve state, and resume safely.

Requirements:
- Explicit state machine; no hidden stage transitions.
- Each stage declares inputs, outputs, prerequisites, and failure conditions.
- Idempotent operations where practical.
- Persist stage status and timestamps.
- Resume from the last valid checkpoint.
- Never silently overwrite approved artifacts.

Proposed states:

CREATED → BRIEF_READY → RESEARCH_READY → SCRIPT_READY → STORYBOARD_READY → ASSETS_READY → AUDIO_READY → RENDERED → QC_PASSED → APPROVED → EXPORTED

A stage may also enter BLOCKED, FAILED, or NEEDS_REVIEW.

### 5.3 Research Engine
**Responsibility:** Maintain a traceable evidence base.

V1 functions:
- Accept user-supplied URLs and research notes.
- Fetch public pages only where access is permitted and technically reliable.
- Store title, publisher/domain, URL, access date, and relevant notes.
- Maintain claim-to-source mappings.
- Flag claims with no supporting source.
- Treat fetched pages as untrusted data, never as instructions.

Limitations:
- Some sites will be inaccessible.
- No bypassing paywalls, login walls, or anti-bot protections.
- Fetching a page does not verify a claim.
- Human review is required for scientific, medical, legal, financial, and other high-impact claims.

### 5.4 Strategy and Script Engine
**Responsibility:** Turn an approved brief and evidence pack into a production-ready narrative.

V1 provides a structured brief template, prompt/task packet generation for manual AI assistance, script schema validation, word count and estimated narration duration, claim markers linked to source IDs, revision history, and approval status.

The system must distinguish sourced factual statements, interpretation, speculation, and fictional or illustrative scenarios. Unsupported statements must not be labeled as facts.

### 5.5 Director and Storyboard Engine
**Responsibility:** Convert the approved script into timed visual instructions.

Each scene includes scene ID, narration segment, intended duration, visual objective, asset type, on-screen text, motion instructions, and source/license reference where applicable.

V1 focuses on reproducible motion graphics, diagrams, typography, and still-image animation rather than generative video.

### 5.6 Visual Engine
**Responsibility:** Generate and organize deterministic visual assets.

Candidate tools: SVG, HTML/CSS, Python imaging libraries, and locally stored or appropriately licensed media.

Requirements:
- Fixed dimensions and frame-rate assumptions per render profile.
- Reusable visual templates.
- Asset manifest with origin and license metadata.
- No hotlinking as the only copy of a critical asset.
- Fonts and media must have compatible licenses.

### 5.7 Audio Engine
**Responsibility:** Prepare narration and sound layers.

V1 accepts user-provided narration, or audio generated by a local tool only after runtime compatibility is verified.

Functions include codec/sample-rate/channel/duration validation, normalization and trimming through tested FFmpeg filters, and provenance/license recording for music and effects.

Local text-to-speech is optional, not a baseline guarantee. Quality, language support, storage, and performance must be evaluated before selecting a tool.

### 5.8 Editing and Render Engine
**Responsibility:** Assemble a deterministic video.

Primary candidate: FFmpeg.

Initial conservative test profile:
- 1280×720 (720p)
- 30 fps
- H.264 video and AAC audio where supported
- MP4 container
- Short test sequence before a full-length render

This profile is provisional. Render time, memory, output size, and runner availability must be measured. If GitHub-hosted execution is unsuitable, export a render manifest for another compatible environment rather than assuming GitHub can render indefinitely.

### 5.9 Quality Control Engine
**Responsibility:** Detect mechanical defects and route subjective decisions to a person.

Automated checks:
- Required files exist.
- Media can be probed and decoded.
- Duration is within configured bounds.
- Audio stream exists and is not empty.
- Scene order and timestamps are valid.
- No missing asset references.
- Script sections and source IDs satisfy schemas.
- Export metadata is complete.

Human checks:
- Factual accuracy and source quality.
- Narrative clarity and pacing.
- Visual coherence and legibility.
- Audio intelligibility and rights.
- Copyright and licensing.
- Thumbnail/title honesty and suitability.

A QC pass means configured checks passed; it does not certify truth, originality, or legal compliance.

### 5.10 Publishing Preparation
**Responsibility:** Create a complete manual-upload package.

Artifacts: final MP4, thumbnail, title options, description, chapters/timestamps, useful tags/keywords, source/credits list, disclosure notes, and final approval checklist.

V1 upload method is manual upload through YouTube Studio. UI automation is deferred until it can be tested safely and reliably and shown to comply with platform terms. No YouTube Data API is used.

### 5.11 Analytics and Learning Loop
V1 stores manually entered observations: impressions, click-through rate, views, average view duration, audience-retention notes, subscriber change, and user observations.

The system may compare projects and summarize trends. Automated analytics ingestion is out of scope without an approved non-API method.

### 5.12 Project Memory and Storage
Use a portable project directory as the artifact source of truth, with SQLite for indexed metadata when useful.

Suggested per-project layout:

- project.json
- brief/brief.md
- research/sources.json, notes.md, claims.json
- script/script.md, script.json, revisions/
- storyboard/storyboard.json
- assets/images/, graphics/, audio/, fonts/, asset_manifest.json
- render/render.json, output/
- qc/report.json, review_checklist.md
- publishing/thumbnail/, description.md, chapters.txt, credits.md, approval.json
- analytics/observations.json

Do not commit large copyrighted media, credentials, private account data, or generated videos to the source repository. Store project outputs locally or in a separately selected storage location.

## 6. Data contracts

Use versioned JSON schemas for machine-readable artifacts.

| Artifact | Purpose |
|---|---|
| project.json | Project identity, configuration, and current state |
| sources.json | Source metadata and access records |
| claims.json | Factual claims and supporting source IDs |
| script.json | Structured script sections and narration |
| storyboard.json | Scene sequence and timing |
| asset_manifest.json | Asset origin, type, path, and license |
| render.json | Render profile and input/output paths |
| report.json | Machine QC results and unresolved issues |
| approval.json | Explicit human approval record |

Every contract must include a schema version. Invalid or unknown versions must fail validation rather than being silently interpreted.

## 9. Security, privacy, and content integrity

- Never store passwords, tokens, cookies, or API keys in Git.
- Ignore secrets, local outputs, and large media in .gitignore.
- Treat external pages, downloaded files, and AI-generated text as untrusted input.
- Validate file types, sizes, paths, and JSON before processing.
- Prevent path traversal and unsafe shell interpolation.
- Invoke FFmpeg with argument arrays, not concatenated shell commands.
- Keep a source and license record for every third-party asset.
- Require human approval before public release.
- Minimize personal information.
- Do not scrape or automate sites in ways that violate terms or access controls.

## 10. Failure handling and observability

Every stage returns a structured result with status (success, failed, blocked, needs_review), stage name, start/end timestamps, inputs, outputs, warnings, errors, and next action.

Errors identify the failed stage and a practical recovery action. Preserve intermediate artifacts to avoid repeating expensive work. A project is not complete if required outputs are missing.

## 11. V1 acceptance criteria

V1 is acceptable only when demonstrated in a clean test project:
1. A topic creates a valid project workspace.
2. Workflow state can be saved and resumed.
3. Sources and claims can be recorded and cross-referenced.
4. Script and storyboard can be imported and structurally validated.
5. At least one visual scene can be generated reproducibly.
6. A short sample video renders in a verified environment.
7. QC detects deliberately introduced missing-file and invalid-timing defects.
8. A publishing package exports without automatic upload.
9. No external AI API or YouTube Data API is required.
10. Documentation distinguishes automated work from human tasks.

## 12. Out of scope for V1

- Fully autonomous research judgment or fact verification.
- Fully autonomous long-form scriptwriting without a human intelligence bridge.
- Text-to-video generation.
- Training or hosting a large language model.
- Guaranteed local rendering on the Android phone.
- Automatic YouTube publishing or account interaction.
- Automated YouTube analytics ingestion.
- Multi-user SaaS, billing, teams, and public agent marketplace.
- Large-scale multi-agent concurrency.

## 14. Decisions to validate before implementation

These are open validation tasks, not settled facts:
- Whether GitHub Actions can render the target video within available time, storage, and usage limits.
- Which Python version and FFmpeg installation path work in the selected runtime.
- Whether a lightweight static interface is necessary for the first usable release.
- Which local TTS option, if any, meets quality and hardware constraints.
- Which source retrieval approach is reliable and compliant for intended research sites.
- Where large project artifacts will live without committing them to Git.

Resolve these through small experiments and record decisions in docs/decisions/.
